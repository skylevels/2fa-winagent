# Проверка перед вводом в эксплуатацию

Эти проверки требуют отдельного тестового домена с двумя Windows Server 2022 DC и клиентами Windows 10/11. Автоматические PHP-тесты не подтверждают фактическое поведение Windows, RDP, Kerberos, PowerShell 5.1, антивируса или AD. Проверки из этой инструкции не выполнялись автоматически на рабочем домене.

## Подготовка

Создать тестового обычного пользователя, два компьютера и `2fabypass`. Группу создать один раз на одном DC и дождаться репликации на второй. Проверить DC FQDN, синхронизацию часов, репликацию, запрет NTLM согласно принятой политике домена, расположение PHP/кода и права конфигурации. Целевые рабочие серверы — `dosifey.elemer.org` и `pimen.elemer.org`; испытания сначала выполнять в тестовом домене. Настроить каждому агенту свой `agentId`, локальный DC и постоянный исходящий IP сервера мобильной авторизации в `allowedIPs`. В `apiSecretHex` оставить заглушку; ключ создаётся установщиком на целевом DC. Код размещается в `C:\2fa\agent`, конфигурация — `config.json`, журналы — `C:\2fa\logs`, инструкции — `C:\2fa\docs`. Разместить одинаковую заглушку на обоих узлах.

Имена компьютеров в `userWorkstations` не являются доказательством успешной мобильной аутентификации. Проверяется фактический вход Windows и события безопасности, а не только содержимое атрибута.

## Установка с загрузкой компонентов

1. На чистом тестовом DC запустить `deploy/Install-AgentOnline.ps1` в повышенной 64-битной Windows PowerShell 5.1. Проверить загрузки, выпуск `WebServer10y`, отдельный HMAC, запуск задачи на 8443 и создание `C:\2fa\docs`, `logs`, `distrib`.
2. До записи кода проверить настоящие NTFS-права новых `C:\2fa` и временной папки: обычный пользователь не может читать или менять содержимое. Существующий каталог с посторонним владельцем/правом записи, reparse point, занятой 8443 или уже установленный агент должны приводить к отказу без перезаписи установки.
3. На стенде проверить обрыв/зависание загрузки, неверный SHA-256, чужую подпись VC++ и небезопасный ZIP. Установка/запуск не должны продолжаться; отдельная загрузка ограничена общим сроком 120 секунд, VC++ — пятью минутами.
4. Проверить VC++ с кодом 3010: агент ещё не размещён и не запущен, после перезагрузки возможен повтор. При ожидающем одобрения запросе CA файлы должны сохраняться; получить сертификат через `Request-AgentCertificate.ps1 -RequestId`, затем завершить локальную установку и запуск по инструкции. Время ожидания `certreq` определяется Windows/CA и отдельно скриптом не ограничивается.

## HTTPS и сертификаты

1. До установки проверить PHP `openssl`, свободный порт 8443 и пути `tlsCertificateFile`/`tlsPrivateKeyFile` в `C:\2fa\agent\tls`. Убедиться, что при занятом порте 8443 (например, IIS на Dosifey) установщик отказывает до изменений ACL/задач и не останавливает существующую службу. Все проверки выполнять с реальным Windows PowerShell 5.1 и CA на Dosifey.
2. На каждом DC запросить отдельный сертификат готового шаблона `WebServer10y`, опубликованного на CA Dosifey. Проверить SAN соответствующего FQDN, Server Authentication, соответствие закрытому ключу и доверенную цепочку. Сверить pKIExpirationPeriod шаблона (десятилетний интервал 3650–3653 дня) и фактические NotBefore/NotAfter. Убедиться, что сокращение срока более чем на сутки прекращает выпуск без замены рабочих файлов; интервал 3650 дней должен проходить проверку.
3. Проверить успешное подключение с мобильного сервера к `https://dosifey.elemer.org:8443` и `https://pimen.elemer.org:8443` с проверкой CA и имени. Недоверенный CA, неверное имя, истёкший сертификат и подмена сертификата должны отвергаться клиентом до отправки команды.
4. Проверить отказ TLS 1.0/1.1 и незашифрованного HTTP, отсутствие HTTP-порта/перенаправления, сохранение IP/HMAC-проверок внутри TLS. Проверить работу только трёх маршрутов API и отсутствие массовых операций через HTTPS.
5. Обычный пользователь не читает закрытый ключ и не подменяет TLS-файлы. Отсутствующий/повреждённый ключ, несовпадающий сертификат и недоступный файл должны препятствовать запуску агента.
6. Проверить полный архив в `C:\2fa\distrib`: TLS-сертификаты и ключи исходного DC отсутствуют. При переносе на другой DC новый сертификат запрашивается до установки. Веб-панель мобильной авторизации и её сетевые настройки не должны изменяться.

## Установка API-ключа

1. Установить из конфигурации с заглушкой `apiSecretHex`: после защиты NTFS должен появиться случайный ключ из 64 hex-символов. Установка на другом DC создаёт отдельный ключ.
2. Проверить новую установку с заранее заполненным тестовым ключом: установщик заменяет его. В выводе, журналах и переносимом архиве действующего ключа нет.
3. После успешной установки вручную перенести ключ в настройки соответствующего агента портала и проверить подписанный запрос с разрешённого IP. С чужим ключом или IP — отказ.
4. Повторно запустить установщик при существующей задаче: он отказывает, прежний ключ не меняется. После удаления и новой установки создаётся новый ключ; прежний ключ портала больше не подходит.
5. Проверить, что установщик не меняет настройки мобильного портала. Перенос ключа выполняет администратор.

## API и подписи

1. Правильная подпись/разрешённый IP: выдача выполняется на указанном локальном DC.
2. Неверный IP при правильном секрете, поддельный `X-Forwarded-For`, изменённое тело, путь, `agentId`, timestamp или подпись: отказ без изменения AD.
3. Повтор nonce, старое время, тело больше 16 KiB, не-JSON/массив вместо объекта, неизвестный маршрут: отказ.
4. Повтор `request_id` с новым nonce и тем же телом: срок не продлевается. Тот же ID с другим телом: конфликт, без изменения AD.
   Новая команда с уменьшенным либо уже использованным `sequence` отвергается; запоздалое разрешение не отменяет более новый отзыв.
5. Проверить подпись ответа; подменённый ответ не должен становиться успехом в мобильном портале.
6. HTTPS API содержит только выдачу, отзыв и статус: прежние административные пути не выполняются даже с loopback и действующим API-ключом. Неизвестные ключи не принимаются. Административная CLI с обычной учётной записью не читает приватную конфигурацию и не подключается к именованному каналу.

## Пользователи и списки

1. Существующий список `PC-A,PC-B`: выдача `PC-C` сохраняет все три значения. Повторное разрешение той же пары не добавляет дубликаты.
2. Разрешить `PC-A` на пять минут; через минуту продлить ещё на пять. Старый локальный срок не снимает новое разрешение.
3. Разрешить `PC-A` до T+3 и `PC-B` до T+5. В T+3 должен остаться **только** `2FA-BLOCK`; разрешение `PC-B` также прекращается.
4. Отзыв `PC-A` при наличии `PC-B` удаляет только `PC-A` и добавляет отсутствующую заглушку.
5. Логин не найден/неоднозначен, неправильные символы, слишком длинное имя ПК, слишком большой список: понятная ошибка, без записи неверного значения.
6. Создание в тестовом AD компьютерного объекта с именем заглушки: дальнейшие изменения должны блокироваться. После теста устранить конфликт штатным администрированием.

## Исключения

Для каждой операции API, истечения срока, массового включения и выключения сравнивать атрибут до/после. Проверять:

- прямого участника `2fabypass`: никаких изменений;
- участника группы, вложенной в `2fabypass`: обход не применяется;
- пользователя с `2fabypass` как основной группой;
- встроенного Administrator, в том числе переименованного;
- прямого и вложенного участника Domain Admins, Enterprise Admins, BUILTIN Administrators;
- пользователя с административной основной группой;
- пользователя, которого добавили в исключение после выдачи, до истечения таймера: агент не меняет его даже при очистке;
- отсутствующую/недоступную группу исключения: ошибка без небезопасного продолжения записи.

## Локальные команды и именованный канал

Проверки выполнять на Windows Server 2022 с Windows PowerShell 5.1; в Linux невозможно подтвердить реальные Windows ACL именованного канала. Проверить запуск агента под SYSTEM и выбранной gMSA, если она используется.

- Повышенная консоль администратора на этом DC подключается к каналу; обычная и неповышенная консоли доступа не получают.
- Попытка соединиться с каналом по сети отвергается, в том числе от администратора другого сервера.
- При остановленном агенте CLI завершается с понятной ошибкой и не выполняет самостоятельную запись AD.
- Повторный запуск агента не позволяет занять тот же канал и обрабатывать команды вторым процессом.

Массовые операции выполнять только командами `agentctl.php` из повышенной консоли на соответствующем DC:

1. Предварительный просмотр не меняет пользователей, таймеры или режим.
2. Применение включения добавляет заглушку к существующим значениям; исключённые пользователи не изменяются.
3. Применение выключения полностью очищает атрибут обычных пользователей, прекращает все местные таймеры и блокирует новые выдачи.
4. Оставить агента работать больше пяти минут после выключения: заглушки не должны появиться из его прежних таймеров.
5. Вызвать выключение только на одном DC и подтвердить ожидаемое ограничение: второй агент не получает команду автоматически и способен вернуть заглушки своим таймером. Если до этого команды обрабатывали оба агента, выполнить локальное выключение на каждом для отмены всех местных таймеров.
6. Смоделировать отказ записи части пользователей: результат обязан отражать ошибки/частичную обработку. После исправления прав повторить локальную команду.
7. Во время обхода проверить `bulk_running: true`, доступность статуса и отказ HTTP 409 для новых выдач/отзывов. Убедиться, что между пакетами выполняются истёкшие таймеры, а операция выключения не ждёт бесконечной очереди неудачных очисток.
8. Закрыть консоль либо прервать ожидание локального ответа: выяснить через статус, продолжается ли обход. Частичный итог должен дать CLI ненулевой код завершения; выключенный режим должен сохраняться даже при неудачной очистке AD.

## Dosifey первым, Pimen при недоступности

1. При доступном Dosifey отправить выдачу, продление и отзыв через портал. Проверить обращение только к Dosifey: запроса на Pimen и ожидания его подтверждения нет.
2. Остановить Dosifey либо прервать связь портала с ним. После ошибки соединения/таймаута портал отправляет ту же команду Pimen: исходные байты тела, request_id, sequence и expires_at сохранены, timestamp/nonce и подпись сформированы заново с agentId и ключом Pimen.
3. Получить подписанный отказ операции от Dosifey, например HTTP 409. Портал должен обработать отказ, не обходя его через Pimen.
4. Восстановить доступность Dosifey. Следующая новая команда направляется на него; агенты не обмениваются ролями, таймерами или состоянием.
5. Потерять ответ Dosifey после записи AD, затем отправить запрос Pimen. Зафиксировать допустимое выполнение на обоих после неопределённого исхода: общего подтверждения/истории команд между агентами нет, автоматическая компенсация не запускается.
6. Выдать разрешение через Dosifey, затем при его недоступности продлить через Pimen. Возврат Dosifey может привести к удалению разрешения его прежним таймером. Это принятое ограничение редкого сбоя; автоматическая сверка не требуется.
7. Перезапустить агент с активным разрешением: таймер исчезает, запись AD остаётся. Проверить отсутствие восстановления с диска, передачи таймера другому агенту и обязательной повторной рассылки прежних команд.
8. Изолировать репликацию в тестовом домене: изменения не появляются мгновенно на другом DC. После восстановления проверить итоговое значение AD; отдельного протокола согласования агентов нет.
9. Перезапустить ранее выключенный агент: проверить режим из `startEnabled`. Для длительного выключения эта настройка должна быть `false` на обоих узлах.
10. Временно запретить запись AD: таймер не считается успешно исполненным, ошибки видимы в состоянии/ответах; работающий агент повторяет свою очистку после восстановления AD.
11. Проверить таймаут PowerShell-процесса, аварийный выход PHP и задачу перезапуска. Повторный экземпляр на том же сервере не получает занятой API-порт и не обслуживает команды параллельно.

## Задержки и устойчивость к медленным клиентам

1. Замерить выдачу и отзыв на обоих DC при первом запуске и обычной нагрузке; отдельно проверить задержки поиска, записи и истечения. Портал проверяет доступность за 3 секунды и ждёт команду отдельно до 130 секунд по умолчанию; адаптер AD — до 30 секунд на каждый процесс: при превышении бюджета возможна поздняя запись после обращения к другому агенту.
2. Задержать текущую AD-операцию и отправить следующую команду. После `queueWaitTimeoutSeconds` и ближайшего секундного такта ожидающая HTTP-команда должна получить 504, исчезнуть из очереди и не записаться позднее. Локальная команда выключения сохраняет приоритет и отдельный срок ожидания.
3. Подключиться с разрешённого IP и остановиться на TLS handshake, неполных HTTP-заголовках или теле. Соединение должно закрыться в пределах `requestReceiveTimeoutSeconds`, а следующие обычные команды должны успешно работать. Проверить немедленное отклонение тела больше 16 KiB и лимит `maxConnections`.
4. Проверить работу через IPv6, если он используется. Неразрешённый IP должен отклоняться до TLS, независимо от `X-Forwarded-For`.
5. Проверить неизвестный логин: ответ 404 не переводит исправный каталог в `ready: false`. Проверить синхронизацию часов портала и DC: HMAC-окно не допускает срок выдачи больше настроенного значения по часам агента.
6. На отдельном стенде проверить перевод часов назад во время ожидания/поиска: срок разрешения и ожидание CLI не продлеваются. Не менять время рабочего DC ради этого испытания.
7. Измерить массовый обход на фактическом числе пользователей. Пока каждый пакет повторно читает весь домен, увеличение числа пользователей повышает нагрузку быстрее линейной. Проверить отчёт о частичном результате при таймауте, доступность статуса и очистку между пакетами.

## Повтор ручного отзыва после временной ошибки

1. Для обычной пары, затем отдельно для support, выдать доступ и отправить ручной отзыв с новым UUID/sequence. На стенде вызвать временную ошибку AD. Восстановить AD и повторить то же тело с теми же UUID/sequence, но новым timestamp/nonce/HMAC. Ожидать подтверждённый `revoked`; ещё один повтор не должен записывать AD повторно.
2. Повторить при уже завершившейся внутренней очистке агента: прежняя ошибка не должна навсегда заменять успешный результат нового исполнения отзыва. Проверить такой же первый повтор после обычного TTL 600 секунд в изолированной проверке агента. Портал по своему правилу повторяет ручной отзыв только до исходного срока разрешения.
3. После неудачного отзыва успешно отправить более новую выдачу тому же пользователю. Старый failed-revoke должен получить 409 без записи AD. Проверить также смену режима pair/support и повтор с изменённым телом либо endpoint.
4. На отдельном тестовом пользователе проверить смену AD GUID за прежним логином: старый отзыв не должен затронуть другую учётную запись. Выключенный режим и массовая операция обязаны по-прежнему запрещать повтор.

## Настраиваемые сроки

1. В отдельной конфигурации проверить обычный доступ при grantDurationSeconds=30 и 600, support при supportDurationSeconds=30 и 180. Таймер и возвращённый expires_at должны соответствовать выбранному сроку; до его конца доступ сохраняется, затем запускается очистка.
2. Значения 29/601 для обычного и 29/181 для support, а также строки/дроби/boolean, должны запрещать запуск. Отсутствующие поля используют 300/60.
3. Проверить, что /v1/status возвращает оба целочисленных значения с верной подписью и портал строит таймер по ним. Несовпадение настроек другого адресата не должно незаметно менять общий дедлайн уже отправленной выдачи.
4. Новая команда с expires_at за пределом настройки не записывается; время очереди, поиска, повтора и изменения часов не добавляется к допустимому окну. Запрос с небольшим оставшимся сроком не отвергается лишь потому, что он меньше минимального значения настройки 30.
5. Изменение файла применяется после запуска нового процесса. Испытать без активных разрешений и pending_cleanup; не терять рабочие RAM-таймеры ради смены настройки.

## Реальный вход Windows

Проверять отдельно Windows 10 и Windows 11, локальный вход, новый RDP-сеанс, подключение к существующему RDP-сеансу и разблокировку. Снять разрешение, сохранив открытый сеанс: работа в нём должна продолжаться.

Для разблокировки учитывать кэширование учётных данных. Microsoft описывает сочетание политик `Interactive logon: Require Domain Controller authentication to unlock workstation` и `Interactive logon: Number of previous logons to cache (in case domain controller is not available) = 0`. При отсутствии DC такое сочетание ограничивает вход/разблокировку. Применять политики отдельно в тестовом OU и проверить фактическое поведение; установщик агента GPO не меняет. [Описание Microsoft](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-require-domain-controller-authentication-to-unlock-workstation).

Проверить сценарии с доступным и недоступным DC, свежими и ранее полученными Kerberos-билетами, NLA/RDP и принятыми в организации способами входа. `userWorkstations` сам по себе не является универсальным механизмом MFA для всех протоколов и не завершает действующие сеансы. Microsoft рекомендует другие права входа для новых решений; выбранную схему считать пригодной только для тех сценариев, которые подтверждены стендом. [User-Workstations](https://learn.microsoft.com/en-us/windows/win32/adschema/a-userworkstations).

Открытый код не отменяет проверки антивирусом/EDR. Испытать точную сборку PHP, PowerShell-скрипты, запуск из планировщика и работу с AD под выбранной учётной записью, не выключая защиту. Зафиксировать версии, политики и результаты до распространения на рабочий домен.

## Доступ к файлам и журналы

1. После установки проверить NTFS ACL корня `C:\2fa`, кода, `config.json`, документации, журналов и PHP: Administrators, Domain Admins и SYSTEM имеют доступ; обычный доменный пользователь не может читать код/секреты/журналы и заменять каталоги через права родителя. Проверить также вложенные файлы с ранее заданными широкими ACL.
2. Для gMSA проверить чтение/запуск кода и запись журналов без права изменять код/конфигурацию. Убедиться, что отказ обычному пользователю не реализован через Deny для Domain Users, блокирующий и администраторов.
3. Выполнить выдачу, отзыв, истечение и ошибку AD: соответствующие события должны попасть в дневной JSONL. Ключи, подписи, полные HTTP-тела и исходные исключения не должны сохраняться. Проверить UTC в метках времени.
4. В отдельной папке с тестовыми журналами проверить упаковку завершённого месяца, сохранение текущего месяца и существующего архива, повтор запуска без потери данных, отказ на повреждённом архиве с сохранением исходников.
5. Проверить границу трёх календарных лет, високосный год, удаление по периоду имени и сохранение посторонних файлов. Архив удаляется только после устаревания всего месяца.
6. Проверить задачу `TwoFactorAgent-LogMaintenance`: запуск при загрузке, ежедневно в 03:15 по времени сервера, недопущение параллельных запусков и ненулевой результат при ошибке. После удаления задачи/агента код, документы и существующие журналы должны сохраняться.
