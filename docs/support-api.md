# API временного доступа техподдержки

Дополнение к обычному API агента. Обычные `/v1/grants` и `/v1/revocations` сохраняют контракт «логин + компьютер» и настраиваемый срок grantDurationSeconds (по умолчанию 300 секунд). Режим техподдержки использует отдельные маршруты и срок **supportDurationSeconds: 30–180 секунд, по умолчанию 60** до абсолютного `expires_at`.

## Обнаружение поддержки

Подписанный `POST /v1/status` с телом `{}` содержит прежние поля и:

```json
{
  "capabilities": ["support_all_v1"],
  "active_support_grants": 0
}
```

`active_grants` включает обычные разрешения и разрешения техподдержки; `active_support_grants` считает только последние. Это локальные записи агента, а не подтверждение успешного Windows-входа. До подтверждённой очистки истёкшая запись может оставаться в счётчике.

Портал проверяет подпись, идентификатор агента, `enabled`, `ready` и наличие `support_all_v1`. Отсутствующая capability, неподписанный ответ или неизвестный endpoint запрещают выдачу support-доступа. Подмена support-заявки обычной заявкой с особым значением `computer` не допускается.

## Настройка длительности

В `C:\2fa\agent\config.json` поле `supportDurationSeconds` задаёт целое число секунд от 30 до 180, по умолчанию 60. Обычный доступ задаётся отдельным `grantDurationSeconds`: 30–600, по умолчанию 300. `/v1/status` сообщает оба значения как `support_duration_seconds` и `grant_duration_seconds`; портал берёт нужный срок перед отправкой. Настройки участвующих агентов должны совпадать. Тело запроса по-прежнему содержит абсолютный `expires_at`, а не новую относительную длительность.

Конфиг перечитывается при запуске. После ручного изменения требуется перезапуск; сначала дождаться завершения и очистки текущих разрешений, поскольку таймеры только в RAM. Оставшееся до expires_at время при доставке может быть меньше 30 секунд; диапазоны ограничивают настройку, не задержку сети.

## Аутентификация

HTTPS 8443, доверенный сертификат с проверкой DNS-имени, точный список разрешённых IP и существующий ключ `mobile`. Заголовки и HMAC-SHA256 совпадают с обычным API. Ключ — 32 байта после декодирования 64 шестнадцатеричных символов. В подпись запроса включается **полный фактический путь** `/v1/support/grants` либо `/v1/support/revocations`:

```text
POST
PATH
AGENT_ID
TIMESTAMP
NONCE
SHA256_RAW_BODY_HEX
```

Разделитель LF, без завершающего LF. При каждом сетевом повторе новый nonce и timestamp; request_id, sequence и expires_at сохраняются. Подпись ответа прежняя: `RESPONSE`, agent ID, nonce запроса, HTTP-код, SHA-256 тела; LF без завершающего LF. Секреты, SMS-коды и доменные пароли не передаются в теле.

## Выдача

`POST /v1/support/grants`

```json
{
  "request_id": "10000000-0000-4000-8000-000000000001",
  "sequence": 1001,
  "login": "support-user",
  "expires_at": "2026-11-05T10:01:00Z"
}
```

Дата в примере иллюстративная. В реальном запросе `expires_at` — UTC `YYYY-MM-DDTHH:MM:SSZ`, строго позже текущего времени агента и не далее supportDurationSeconds от часов агента. Срок задаётся порталом при первой отправке, а не после ответа AD. Время ожидания очереди и выполнения AD не прибавляется к сроку. Агент дополнительно сохраняет монотонный дедлайн, поэтому перевод системных часов назад не продлевает окно.

`login` — простой sAMAccountName до 20 символов, UUID и sequence проверяются как в обычном API. Поля `computer`, `scope`, длительность от клиента и другие лишние поля запрещены. Sequence — положительное целое не больше 9007199254740991.

После проверки исключений агент очищает атрибут `userWorkstations` у найденного пользователя. Пустое значение снимает ограничение по рабочим станциям. Членство в группах, привилегии, пароль и права входа Windows не меняются: пользователь получает возможность новых входов на ПК/серверы только в пределах уже существующих прав AD/Windows.

Успех возвращается после подтверждения требуемого значения на этом DC:

```json
{
  "ok": true,
  "result": {
    "request_id": "10000000-0000-4000-8000-000000000001",
    "user_id": "11111111-1111-4111-8111-111111111111",
    "sequence": 1001,
    "login": "support-user",
    "scope": "support_all",
    "status": "granted",
    "expires_at": "2026-11-05T10:01:00Z"
  }
}
```

Если срок истёк во время поиска пользователя, разрешение не записывается. Если он истёк во время записи, агент не возвращает `granted`, а ставит подтверждаемую очистку. Неопределённый результат записи также требует очистки.

## Отзыв и истечение

`POST /v1/support/revocations`:

```json
{
  "request_id": "10000000-0000-4000-8000-000000000002",
  "sequence": 1002,
  "login": "support-user"
}
```

Агент заменяет весь `userWorkstations` запрещающей заглушкой `2FA-BLOCK` и проверяет результат чтением с этого DC. Результат имеет те же идентификаторы, `scope: "support_all"`, `status: "revoked"`, `expires_at: null`; поля `computer` нет. Восстановления предыдущего произвольного списка ПК нет. Отзыв работает и без локальной записи таймера, например после перенаправления на другой агент. Открытые Windows-сеансы не завершаются.

При истечении срока выполняется такая же полная очистка. Ошибка сохраняет задачу очистки, повторяемую с паузой 5 секунд. Новые разрешения для этого пользователя блокируются до подтверждения очистки. Локальный выключенный режим 2FA (`enabled=false`) отклоняет новые выдачи **и отзывы** HTTP 409: запоздалый отзыв не должен снова устанавливать заглушку после `disable --apply`. Неудачный bulk-disable сохраняет состояние ошибки; 409 не означает успешную очистку и не должен трактоваться порталом как `revoked`.

## Повторы, порядок и разделение режимов

- UUID-кэш общий для команд; fingerprint включает endpoint и все поля тела. Повтор того же UUID на другом endpoint или с изменёнными данными даёт 409.
- Повтор успешно выполненной команды возвращает `status: "already_processed"`, `original_status`, `currently_active` и первоначальный результат. Повтор не выполняет запись и не продлевает срок.
- Неудавшийся отзыв можно повторить с теми же UUID, sequence и телом: перед записью проверяются исходный AD GUID и равенство номера текущему high-water. Более новая принятая команда или другая учётная запись за прежним логином запрещают старый отзыв с 409. Такой failed-revoke остаётся в ограниченном RAM-кэше после обычных десяти минут, пока его номер последний; после успешного повтора действует обычный TTL результата. Ошибки выдачи повторно не исполняются. Выключенный режим и массовый обход по-прежнему запрещают отзыв.
- Sequence монотонно растёт **по стабильному AD user GUID сразу для обоих режимов**. Разделять независимые счётчики pair/support нельзя: тогда старый отзыв одного режима мог бы отменить новое разрешение другого.
- Локальные pair/support leases хранятся раздельно. При действующем разрешении одного режима команды другого режима, включая отзыв, получают 409. Портал также обязан иметь общую блокировку логина между обычным и support-порталом.
- Новая подтверждённая выдача того же support-режима с новым UUID/sequence заменяет локальный дедлайн. Старого независимого callback-таймера нет; предыдущий дедлайн не отменит новое разрешение.
- Успешные результаты живут 10 минут; high-water sequence и описанные выше актуальные неудавшиеся отзывы хранятся до смены номера/перезапуска. Команды в очереди сохраняют общий короткий лимит ожидания. Таймаут клиента не отменяет уже начатую операцию AD.

## Защитные ограничения

Встроенный Administrator, защищённые административные группы и прямые члены `2fabypass` исключены по прежним правилам. Они получают `excluded`, а их атрибуты не изменяются. Проверки членства повторяются непосредственно перед каждой записью и очисткой. Неизвестное членство, отсутствие корректной bypass-группы или коллизия настоящего компьютера с `2FA-BLOCK` запрещают операции. `excluded` не является выданным support-разрешением.

Право использовать техподдержку и свежая SMS-проверка **для каждого открытия окна** проверяются порталом. Windows-агент доверяет разрешённому IP и ключу mobile и не знает состояние SMS или пользователя aidesk. Сохранённая браузерная сессия портала не заменяет это подтверждение. Защита ключа mobile остаётся критичной.

## Пределы гарантии времени

Настроенный срок (по умолчанию 60 секунд) задаёт абсолютный дедлайн разрешения, который агент не продлевает из-за повторов, очереди или перевода часов. Фактическая запись запрета зависит от доступности AD и работы агента. Медленная запись, ошибка очистки, задержка репликации между DC или авария процесса могут оставить разрешение в AD дольше срока.

Как и обычные leases, support-таймеры остаются в оперативной памяти и не восстанавливаются из AD после перезапуска. Портал хранит дедлайн, но не отправляет автоматический отзыв по сроку, при ошибке выдачи или изменении учётной записи. По настроенному сроку портал локально завершает окно, не подтверждая очистку AD; физическую очистку выполняет агент. Только нажатие кнопки пользователя в обычном ЛК создаёт HTTP-отзыв, повторяемый исходным получателям до исходного дедлайна. Если таймер агента потерян, разрешение может остаться без автономной очистки. Гарантировать физическое закрытие строго к настроенному дедлайну при таких отказах текущая архитектура не может; это принятое ограничение независимых агентов и состояния только в RAM.

## Проверка и обновление

В Linux проверены 129 PHP-тестов и 40 PowerShell-тестов с подменённым AD. Покрыты отдельные endpoints, подписи и capability, настроенные сроки и значение по умолчанию 60 секунд, повторы, старые sequence, конфликты режимов, задержанные ответы, перевод часов, ошибки записи/очистки, admin/bypass-исключения и поздние отзывы после выключения. Настоящие AD, Windows PowerShell 5.1, Windows-вход и репликация DC в этой проверке не использовались.

Обновлённый комплект агента должен включать `src/GrantManager.php`, `src/HttpServer.php`, `src/AuditLogger.php`, `powershell/Directory.ps1` и этот документ. Сборка штатным `deploy/New-Distribution.ps1` включает каталоги `src`, `powershell`, `tests`, `docs`; конфигурация и ключи текущей установки сохраняются. До развёртывания обновлённых агентов портал должен считать support-режим неподдерживаемым. Сборка/установка дистрибутива и проверка на контроллере домена выполняются отдельно.
