# HTTPS API агента

Документ для разработчика мобильного портала. Описывает подготовленный контракт агента; развёртывание на контроллерах ещё не выполнялось.

Базовый адрес: `https://<agent-host>:8443`. URL, `agentId` и API-секрет каждого агента задаются настройками отправителя. `agentId` — отдельный идентификатор из конфигурации агента; он не обязан совпадать с DNS-именем сервера. Конкретные серверы и их приоритет указаны в [памятке администратора DokuWiki](instruction.txt). Замена серверов не меняет маршруты, форматы сообщений и алгоритм подписи.

DokuWiki-версия описания API устанавливается в `C:\2fa\docs\api.txt`; исходный файл — [api.txt](api.txt).

Отдельные endpoints техподдержки и capability `support_all_v1` описаны в [support-api.md](support-api.md). Режим снимает ограничение по рабочим станциям на настроенный срок, по умолчанию 60 секунд и не изменяет обычный контракт пары логин/ПК.

Для новой выдачи портал выбирает первый доступный настроенный агент, выполняет подписанный probe `/v1/status` и при неудаче переходит к следующему. Возможные получатели записываются перед отправкой команды. Продление обычной пары и отзыв направляются всем зафиксированным получателям этой выдачи; они закреплены за исходными адресами и не переадресовываются другому DC. Между агентами нет обмена таймерами.

Переход при новой выдаче допускается также после отказа или непроверенного ответа. Сохраняются тело, `request_id`, `sequence` и `expires_at`; timestamp/nonce и подпись создаются заново для адресата. Таймаут не доказывает отсутствие записи AD: такой получатель сохраняется для возможного ручного отзыва до исходного дедлайна. Для probe действует общий лимит 3 секунды, для AD-команды — отдельный конечный бюджет портала, по умолчанию 130 секунд.

API доступен только по HTTPS, порт по умолчанию — 8443; минимальная версия TLS — 1.2. Открытого HTTP и перенаправления с HTTP нет. Все маршруты принимают только `POST` с `Content-Type: application/json`. Тело — JSON-объект, не более 16 KiB. Query string не поддерживается. TLS шифрует соединение; проверка IP и HMAC остаётся обязательной.

Сервер мобильной авторизации должен доверять CA, выпустившему сертификаты агентов, и проверять цепочку, срок и DNS-имя сертификата. Подключаться по FQDN из настроек; отключать проверку сертификата нельзя. Публичная цепочка для настройки доверия находится на DC в `C:\2fa\agent\tls\ca-chain.pem`; закрытый ключ агенту нужен локально и не передаётся отправителю. HTTPS касается API агентов; веб-панель мобильной авторизации этой настройкой не изменяется.

## Ограничения ожидания

По умолчанию агент принимает не больше 100 одновременных соединений. На TLS, заголовки и полное тело запроса отводится 5 секунд от принятия TCP; медленная передача не продлевает этот срок. Соединение закрывается после ответа, поэтому следующий запрос использует новое соединение.

Ожидание команды в очереди ограничено 2 секундами с проверкой также на фоновом такте раз в секунду. Просроченная команда получает HTTP 503 и не начинает запись AD. Уже начатая операция имеет отдельный таймаут: 30 секунд на один процесс PowerShell; для запроса могут потребоваться несколько процессов. Потеря соединения или таймаут отправителя не отменяют начатую запись. HTTP 504 сам по себе не доказывает отсутствие изменений AD.

Настройки: `maxConnections`, `requestReceiveTimeoutSeconds`, `queueWaitTimeoutSeconds`, `processTimeoutSeconds`. Время ожидания отправителя нужно проверить на реальных операциях AD; короткий таймаут способен вызвать обращение к резервному агенту при ещё работающем основном. Часы должны быть синхронизированы: допустимое расхождение HMAC не увеличивает настроенный срок выдачи.

## Настраиваемый срок доступа

В защищённом `C:\2fa\agent\config.json` задаются целые секунды:

| Поле | Допустимо | По умолчанию |
|---|---|---|
| `grantDurationSeconds` | 30–600 | 300 (5 минут) |
| `supportDurationSeconds` | 30–180 | 60 (1 минута) |

Значения вне диапазонов, дроби, строки и boolean не допускаются. Если поля отсутствуют в старом конфиге, применяются значения по умолчанию. Конфиг читается при запуске; после ручного изменения требуется перезапуск агента. Перед перезапуском нужно дождаться завершения текущих разрешений и очистки: таймеры хранятся только в памяти.

Подписанный `POST /v1/status` возвращает `grant_duration_seconds` и `support_duration_seconds`. Портал берёт срок выбранного агента перед первой отправкой и сохраняет общий `expires_at`. На всех участвующих агентах значения должны совпадать; несовпадающий срок другого адресата не должен молча менять уже отправленную команду. Сетевой повтор срок не продлевает. Указанные диапазоны ограничивают **значение настройки**, а не оставшееся время доставки: к получению команды до `expires_at` может оставаться меньше 30 секунд. Агент принимает только будущий абсолютный срок не дальше настроенного значения.

## Подпись запроса

| Заголовок | Значение |
|---|---|
| `X-2FA-Key-Id` | `mobile` |
| `X-2FA-Timestamp` | Целое Unix-время отправки в секундах |
| `X-2FA-Nonce` | 16 случайных байт, 32 строчных шестнадцатеричных символа |
| `X-2FA-Signature` | HMAC-SHA256, 64 строчных шестнадцатеричных символа |

Установщик на каждом сервере генерирует отдельный случайный секрет: 32 байта, сохранённые как 64 hex-символа в `apiSecretHex` защищённого `config.json`. После установки администратор переносит его в настройки соответствующего агента на портале. Секрет не является константой протокола и не входит в дистрибутив.

Ключ HMAC — **бинарные 32 байта**, полученные hex-декодированием `apiSecretHex`. Использовать строку из 64 символов непосредственно как ключ нельзя.

Для проверки реализации отправителя есть [контрольный пример подписи](hmac-test-vector.json), рассчитанный независимой реализацией HMAC. Его ключ публичный, дата фиксированная: это пример для проверки вычислений, а не рабочий запрос или секрет.

Каноническая строка UTF-8 содержит шесть строк, разделённых одним `LF` (`\n`), без завершающего перевода строки:

```text
POST
/v1/grants
AGENT_ID
UNIX_TIMESTAMP
NONCE_HEX
SHA256_RAW_BODY_HEX
```

Третья строка — точный `agentId` адресата. Последняя — SHA-256 **исходных байтов HTTP-тела**, в нижнем hex-регистре. Сначала сериализовать JSON один раз, затем подписать и отправить именно эти байты. Не пересериализовывать тело после вычисления подписи.

В `config.json` агента администратор задаёт `allowedIPs` — список точных IP, с которых разрешены запросы мобильного сервера. Агент сравнивает с этим списком реальный IP TCP-клиента; `Forwarded`/`X-Forwarded-For` не меняют IP для проверки. По умолчанию допустимое отклонение времени — 30 секунд. Нужна синхронизация часов. Повторный nonce отвергается; при транспортном повторе генерировать новый nonce/подпись, сохраняя `request_id`, тело команды и её срок.

HTTPS API предназначен для сервера мобильной авторизации. Массовые изменения и создание группы выполняются только локальными командами администратора на самом DC; они описаны в [инструкции](instruction.txt).

## Подпись ответа

У ответа на аутентифицированный запрос есть `X-2FA-Agent-Id` и `X-2FA-Response-Signature`. Каноническая строка:

```text
RESPONSE
AGENT_ID
REQUEST_NONCE
HTTP_STATUS
SHA256_RAW_RESPONSE_BODY_HEX
```

HMAC-SHA256 вычисляется тем же бинарным ключом. Клиент проверяет подпись по исходным байтам ответа, ожидаемым `agentId`, nonce отправленного запроса и фактическому HTTP-статусу. Неподписанный ответ, неверный `agentId`, код ошибки или недоступность нельзя трактовать как разрешение входа. Ошибки до успешной аутентификации могут возвращаться без подписи.

## Маршруты

| Путь | Ключ | Тело | Действие |
|---|---|---|---|
| `/v1/grants` | mobile | `request_id`, `sequence`, `login`, `computer`, `expires_at` | Добавить компьютер и установить таймер |
| `/v1/revocations` | mobile | `request_id`, `sequence`, `login`, `computer` | Удалить указанную пару, обеспечить заглушку |
| `/v1/support/grants` | mobile | `request_id`, `sequence`, `login`, `expires_at` | Допуск по всем рабочим станциям на supportDurationSeconds; см. support API |
| `/v1/support/revocations` | mobile | `request_id`, `sequence`, `login` | Вернуть полную запрещающую заглушку для support |
| `/v1/status` | mobile | `{}` | Состояние этого экземпляра |

Успех означает завершение операции на локальном DC; подтверждение репликации на другой DC в ответ не входит. Исключённый пользователь не изменяется, и такой результат не следует отображать как вновь выданное временное разрешение.

Общий формат ответа — `{"ok":true,"result":{...}}` или `{"ok":false,"error":{"code":"...","message":"..."}}`. Выдача возвращает `result.status = granted` либо `excluded`; отзыв — `revoked` либо `excluded`. У выдачи также есть `request_id`, `user_id`, `login`, `computer`, `sequence`, `expires_at`. Повтор известной успешной команды возвращает `status: already_processed`, `original_status` и `currently_active`; это не новая выдача и не подтверждение того, что первоначальный доступ всё ещё действует.

`/v1/status` возвращает `agent_id`, `enabled`, `ready`, `active_grants`, `pending_cleanup`, `queued_requests`, `bulk_running`, `last_directory_error`, `server_time`, `state_storage: "memory"`, `grant_duration_seconds`, `support_duration_seconds`, `logging_error` и `dropped_log_records`. `ready: false` препятствует выдаче разрешений. HTTP-статус остаётся доступным; отсутствующую `2fabypass` администратор создаёт локально на одном DC. Ошибка журналирования после запуска отображается как `logging_error: log_write_failed` и счётчик потерянных записей; отзыв разрешений при этом продолжается.

`login` — `sAMAccountName` до 20 символов: буквы ASCII, цифры, точка, дефис, подчёркивание; первый символ — буква или цифра. Например, `ivanov-dd`. UPN, `DOMAIN\user`, пробелы и кириллица не поддерживаются. Регистр логина нормализуется. `computer` — имя NetBIOS до 15 символов: буквы ASCII, цифры, дефис; начинается и заканчивается буквой или цифрой, содержит хотя бы одну букву. Например, `IVANOV-2121`. Регистр компьютера нормализуется к верхнему. Имя заглушки `2FA-BLOCK` передавать нельзя. Неизвестные/лишние поля отклоняются.

### Выдача и продление

```json
{
  "request_id": "4c5b8de6-b4b9-4e10-a2c2-86b8f4f24c30",
  "sequence": 1001,
  "login": "ivanov-dd",
  "computer": "IVANOV-2121",
  "expires_at": "2026-11-05T15:05:00Z"
}
```

Пример даты иллюстративный: клиент вычисляет текущий конечный срок UTC. `expires_at` — абсолютное время UTC в точном формате `YYYY-MM-DDTHH:MM:SSZ` (без долей секунды и часового смещения), больше текущего и не дальше настроенного grantDurationSeconds от часов агента. Сетевые повторы не добавляют к нему время. Срок задаётся один раз для команды и сохраняется при повторе, в том числе при обращении к резервному агенту после недоступности основного.

Новое продление получает новый `request_id`. Повтор с прежним `request_id` и тем же телом возвращает `already_processed` без повторного изменения; `currently_active` описывает наличие ещё действующего местного таймера, а не состояние второго DC или действующий сеанс Windows. Один ID нельзя использовать для другой команды или другого тела. Успешные результаты хранятся десять минут в ограниченном кэше; актуальные неудавшиеся отзывы описаны ниже. После удаления записи старый `sequence` по-прежнему запрещает повторное выполнение, пока жив процесс. После перезапуска история отсутствует.

Если сохранённый результат **выдачи** — неподтверждённая ошибка записи, повтор того же ID не запускает выдачу снова. Повторную выдачу оформлять новой командой с новым ID и увеличенным `sequence`. Исходный конечный срок нельзя продлевать лишь из-за транспортной ошибки. Для временно неудавшегося отзыва действует отдельное правило ниже.

`sequence` — обязательное целое число от 1 до 9007199254740991, увеличивающееся для каждой **новой** команды пользователя, включая отзывы. Один общий возрастающий счётчик сервера также подходит. При повторе на резервном агенте после недоступности основного номер сохраняется. Новые номера пользователя растут независимо от выбранного адресата. Старый либо повторно использованный номер новой команды отвергается с HTTP 409. Повтор по `request_id` сохраняет прежний номер. Максимальный принятый номер пользователя хранится до перезапуска, с ограничением числа пользователей. Нумерация защищает от запоздалой доставки в пределах памяти процесса, но не синхронизирует агентов и не сохраняется после перезапуска.

Одновременно могут существовать таймеры разных компьютеров пользователя. Однако истечение **любого** из них по согласованному правилу очищает весь список до заглушки и отменяет остальные локальные таймеры пользователя. Это не независимые сроки доступа на разных ПК. Очистка сериализована с другими операциями AD; текущая операция может задержать её до своего завершения/таймаута. При недоступном AD выполняются повторные попытки; точного удаления в указанную секунду обещать нельзя.

### Досрочный отзыв

```json
{
  "request_id": "c8d9e078-c13d-497d-a315-c69620edf83a",
  "sequence": 1002,
  "login": "ivanov-dd",
  "computer": "IVANOV-2121"
}
```

Удаляется только этот компьютер; остальные остаются. Если заглушки нет, она добавляется. Отзыв допустим и когда локальный таймер потерян после перезапуска: AD проверяется заново, с обязательными исключениями.

После временной ошибки отзыва можно повторять **тот же** `request_id`, `sequence` и тело на том же агенте. Перед повторной записью агент проверяет fingerprint, исходный AD user GUID и то, что этот `sequence` всё ещё является последним принятым для пользователя. Если после неудачного отзыва уже принята более новая команда, старый отзыв получает 409 и не исполняется. Смена учётной записи за прежним логином также даёт 409. Выключенный режим и массовая операция по-прежнему запрещают повтор.

Это правило действует для `/v1/revocations` и `/v1/support/revocations`. Запись о неудавшемся отзыве сохраняется в ограниченном RAM-кэше дольше десяти минут, пока её номер остаётся последним для пользователя; она не теряет возможность повтора из-за обычного TTL. После успешного повтора результат хранится обычные десять минут. Последующие повторы возвращают `already_processed` без записи. При ошибке выдачи такого разрешения на повтор нет.

Портал отправляет досрочный отзыв только по кнопке пользователя до исходного дедлайна. Плановое истечение настроенного срока обслуживается самим агентом; локальный статус `expired` портала не подтверждает физическую очистку AD.

### Одновременное администрирование

При локальном массовом обходе `bulk_running: true`: HTTP-статус доступен, выдачи и отзывы возвращают HTTP 409. После завершения обхода отправитель проверяет режим `enabled` и готовность `ready`. Администратор управляет режимом локальными командами, описанными в [инструкции](instruction.txt).

## Обязанности отправителя

- Для новой выдачи выбирать агента по приоритету; сохранять всех возможных получателей до отправки. Продление и отзыв закреплять за сохранёнными получателями, подтверждать очистку каждого.
- Проверять TLS, HMAC, HTTP-статус и результат ответившего агента.
- Сохранять тело/ID/`sequence`/срок при повторе; заново создавать timestamp, nonce и подпись для выбранного адресата.
- Для нового продления использовать новый ID, увеличенный `sequence` и новый конечный срок.

Агент изменяет AD на своём DC; репликация выполняется самим AD. Локальные таймеры теряются при перезапуске. Портал сохраняет дедлайны и адресатов. HTTP-отзыв создаётся только по кнопке пользователя; по сроку агент очищает доступ самостоятельно. При недоступном DC физический срок очистки не гарантируется. Агенты не имеют общего хранилища таймеров, а репликация не обеспечивает атомарного порядка команд. Открытые сеансы Windows/RDP продолжаются при обычном отзыве и при сбоях.

Маршрутизация и долговечная история получателей реализованы отправителем; локальный агент обрабатывает подписанную команду только на своём DC.

## Ошибки и порядок интеграции

| HTTP | Значение |
|---|---|
| 400 | Неверный JSON, отсутствующие/лишние поля или формат данных |
| 401 | Неизвестный ключ, неверная подпись или время запроса |
| 403 | IP не разрешён |
| 404 | Пользователь или маршрут не найден |
| 405 / 415 | Нужны POST и application/json |
| 409 | Повтор nonce, конфликт ID/sequence, срок вне окна, режим выключен, массовый обход или неподтверждённая очистка |
| 413 / 429 | Превышен размер тела / очередь |
| 500 / 502–504 | Внутренняя ошибка, проблема AD или адаптера; результат записи может быть неизвестен |

1. Задать исходящий IP портала в `allowedIPs` каждого агента. После установки получить у администратора URL, `agentId`, сгенерированный на этом сервере HMAC-секрет и публичную цепочку CA; сохранить их в настройках соответствующего подключения портала.
2. Проверить расчёт HMAC по контрольному примеру. Подписанный `/v1/status` позволяет проверить нужный экземпляр отдельно; готовность основного агента не зависит от ответа резервного. Для выдачи ожидаются `ready: true`, `enabled: true`, `bulk_running: false`.
3. После подтверждения второго фактора создать одну команду: новый UUID, следующий sequence пользователя и конечный срок. Сохранить её для повторов и отправить основному агенту. Если он недоступен, отправить ту же команду резервному, пересчитав подпись для получателя.
4. Проверить TLS, подпись ответа, HTTP-код и `result`. Свежую выдачу подтверждает `granted`; `excluded` означает отсутствие изменения. У повтора `already_processed` проверить `original_status` и `currently_active`; такой ответ подтверждает только сохранённый результат/местный таймер.
5. При потере ответа основного агента обратиться к резервному с теми же байтами тела/ID/sequence/сроком и новой подписью для получателя. Повторы не меняют конечный срок. Если срок уже прошёл, не пересылать устаревшую выдачу; новое подтверждение второго фактора оформляется новой командой.
6. Если агент сообщает неподтверждённую запись, проверить состояние очистки. Для сознательно начатой новой попытки нужны новый UUID и больший sequence. Это отличается от повтора доставки при неизвестном результате.
7. Только после нажатия кнопки создать досрочный отзыв с новым UUID и большим sequence каждому возможному получателю исходной выдачи. Повторять тот же адресный запрос до подтверждения либо исходного дедлайна. По истечении срока портал завершается локально, а агент очищает доступ своим таймером; подтверждения физической очистки от такого локального истечения нет.

`/v1/status` содержит общие счётчики: запроса проверки конкретного пользователя или пары нет. Не создавать такую проверку на основе одного лишь `active_grants`. Агент не завершает существующие сеансы Windows/RDP и не выдаёт токены авторизации порталу.
