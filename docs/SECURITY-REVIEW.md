# Проверка безопасности и задержек — 5 ноября 2026

Первоначальный аудит сохранён как история. После него портал получил отдельные пробы 3 секунды, бюджет команды 130 секунд и постоянных адресатов. Автоматические HTTP-отзывы отменены по решению владельца: только кнопка создаёт ручной отзыв до дедлайна, а по сроку очищает сам агент. Неудавшиеся отзывы теперь безопасно повторяются с прежним UUID/sequence. Актуальный контракт — [API.md](API.md); текущие проверки — [VALIDATION-RESULTS.md](VALIDATION-RESULTS.md). Пункты ниже описывают состояние первоначальной проверки.

Проверены транспорт, подписи, очереди и сроки Windows-агента, исключения пользователей, дочерние процессы, локальная консоль, установка, ACL, секреты и ротация. Дополнительно просмотрены выдача/отзыв на портале, авторизация, доверие прокси и загрузка CA. Рабочие службы и настройки не изменялись. Это проверка исходников и воспроизводимых сценариев в Linux; проверки настоящего домена ещё нужны.

## Исправлено

| Приоритет | Проблема и исправление |
|---|---|
| Высокий | Соединения до получения HTTP-заголовков не имели общего лимита и срока; медленный TLS/HTTP-клиент мог удерживать ресурсы. Добавлены проверка IP до TLS, лимит соединений, общий срок получения TLS/заголовков/тела, немедленное отклонение тела больше 16 KiB. |
| Высокий | Команда могла провести минуты в очереди и исполниться после отказа портала от ожидания. Ожидание HTTP-команды теперь ограничено отдельно; просроченная команда удаляется без записи AD, даже когда текущая операция ещё занята. Уже начатая запись этим не отменяется. |
| Средний | Перевод системных часов назад во время ожидания/поиска пользователя продлевал разрешение. Монотонный срок теперь фиксируется при получении команды; интервалы локальной консоли также не зависят от перевода часов. |
| Средний | Ошибка «пользователь не найден» переводила весь агент в неготовое состояние. Она теперь относится только к этому запросу. |
| Средний | Зависший дочерний процесс мог надолго занять обработчик. Для адаптера AD ограничен ввод в Windows pipe, исправлены отказ неполной передачи, проверка кода выхода и повтор завершения процесса; до подтверждённого выхода новая запись не запускается. У процесса локальной консоли появился отдельный контроль времени жизни. |
| Средний | Экспорт дистрибутива проверял DACL, но не владельца каталогов. Обычный пользователь-владелец мог изменить права. Теперь проверяется и владелец. |
| Низкий | IPv6-адрес в квадратных скобках от сетевой библиотеки не сопоставлялся с разрешённым IP. Нормализация исправлена. |
| Низкий | Проверка EKU сертификата могла принять другой OID с совпадающим префиксом. Требуется точное значение Server Authentication. |

## Пределы ожидания

Значения по умолчанию; добавлены в примеры конфигурации.

| Параметр | Значение | Что ограничивает |
|---|---|---|
| `requestReceiveTimeoutSeconds` | 5 с; диапазон 1–30 | Полное получение TLS/HTTP, от принятия TCP. Отдельные байты не продлевают срок. После получения тела этот таймер не ограничивает запись AD. |
| `maxConnections` | 100; диапазон 1–1000 | Все открытые соединения, включая TLS и неполные HTTP-запросы. Ответ закрывает соединение. |
| `queueWaitTimeoutSeconds` | 2 с; диапазон 1–30 | Ожидание HTTP-команды до начала обработки. Проверяется также фоновым тактом раз в секунду; фактический ответ может запоздать до следующего такта. Локальные административные команды имеют другой срок. |
| `processTimeoutSeconds` | 30 с; диапазон 1–60 | Один процесс PowerShell, а не весь запрос. Раньше настройка допускала 3600 с. Поиск, запись и проверка готовности могут потребовать несколько процессов. |
| `adminTimeoutSeconds` | 3600 с | Ожидание локальной массовой команды в CLI. Закрытие CLI не отменяет принятую операцию и не блокирует API на час. |
| Контроль процесса локального канала | 330 с | Аварийный предел процесса, который обычно ожидает подключение до 300 с. Это не время обработки обычной команды. |

## Осталось проверить или улучшить

1. **Трёхсекундный таймаут портала.** `portal/agent_client.py` прекращает обмен через 3 с, а агент запускает отдельные процессы PowerShell. При превышении этого времени портал может перейти к следующему агенту, пока первый ещё пишет в AD. Поздняя выдача на первом может пересечься с отзывом на втором; общего `sequence` у независимых агентов нет. Это возможно при обычной задержке, без падения DC. Измерить выдачу/отзыв на настоящих серверах под нагрузкой и согласовать бюджет портала. Выбранная схема независимых агентов сохранена.
2. **Различие политики повторов.** В документации контракта агента отказ операции не служит поводом обращаться к другому DC. Текущий портал переходит к следующему слоту также при подписанном отказе; его основная DokuWiki уже описывает этот каскад. Поведение портала в этой проверке не менялось. Нельзя считать эти две политики одинаковыми; особенно проверить ответы `409` при выключении/массовой операции и конфликте `sequence`.
3. **Массовый обход — O(N²).** `Directory.ps1` заново перечисляет и сортирует весь домен для каждого пакета из десяти пользователей. На большом домене это повышает нагрузку и может упереться в таймаут одного пакета. Требуется замер на целевом числе пользователей; исправление должно вводить проверенную серверную пагинацию, а не просто обрезать выборку и пропускать пользователей. Текущий путь не переписан без проверки LDAP-поведения на Windows.
4. **Часы.** Портал задаёт `expires_at` ровно на 300 секунд вперёд; агент проверяет максимум 300 секунд по своим часам. Опережение портала даже на несколько секунд способно вызвать `409`; окно HMAC ±30 секунд этого не исправляет. Проверить синхронизацию портала и DC отдельно от подписи.
5. **Ограничения AD.** Успешная запись `userWorkstations` не доказывает запрет каждого способа входа. Microsoft [не рекомендует этот атрибут для новых ограничений входа](https://learn.microsoft.com/en-us/windows/win32/adschema/a-userworkstations). [Кэшированный вход](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/cached-domain-logon-information) может выполняться без обращения к DC. Нужны проверки локального входа, RDP/NLA, разблокировки, старых Kerberos-билетов, GPO и возможности самого пользователя менять атрибут. Агент GPO не изменяет. Открытые сеансы по требованию сохраняются.
6. **Журналы.** Месячные ZIP и удаление старше трёх лет ограничивают срок, но не объём. Контролировать свободное место. Ошибка записи видна в статусе; очистка разрешений продолжается. Синхронная запись в локальный диск остаётся зависимостью процесса.
7. **Версия веб-сервера портала.** В `requirements.txt` указан Gunicorn 23.0.0, который [больше не получает внимание по безопасности](https://github.com/benoitc/gunicorn/security). Это не подтверждение конкретной эксплуатируемой CVE. Обновление на поддерживаемую ветку требует отдельной проверки Nginx/Gunicorn и развёртывания; в ходе аудита рабочий веб-сервер не обновлялся.

Потеря таймеров при перезапуске, отсутствие восстановления с диска, задержки репликации AD и действие старого таймера после продления другим агентом остаются принятыми ограничениями архитектуры.

## Зависимости и подтверждение

Свежий `composer audit --locked` не обнаружил опубликованных предупреждений в PHP-зависимостях. Полный дистрибутив содержит официальный Windows PHP 8.4.27-1; SHA-256 сверена с метаданными PHP. Это [ветка с исправлениями безопасности](https://www.php.net/releases/8_4_27.php). Установщик допускает PHP 8.2+, поэтому при использовании собственного интерпретатора администратор должен отдельно проверить его актуальность. Заявленный Django 5.2.19 соответствует [выпуску безопасности от 3 ноября](https://www.djangoproject.com/weblog/2026/nov/03/security-releases/).

Точные результаты и границы автоматических проверок — в [VALIDATION-RESULTS.md](VALIDATION-RESULTS.md). План оставшихся испытаний — в [WINDOWS-VALIDATION.md](WINDOWS-VALIDATION.md). Прохождение имитационных тестов не заменяет испытания NTFS, Windows PowerShell 5.1, AD CS, Kerberos и реального входа в домен.
