====== HTTPS API агентов второго фактора ======

Инструкция для разработчика мобильного портала. Контракт подготовлен в коде; развёртывание на контроллерах ещё не выполнялось.

Базовый адрес: ''https://<agent-host>:8443''. URL, agentId и API-секрет каждого агента задаются настройками отправителя. ''agentId'' — отдельный идентификатор из конфигурации агента, он не обязан совпадать с DNS-именем. Конкретные серверы и их приоритет указаны в памятке администратора ''C:\2fa\docs\instruction.txt''. Замена серверов не меняет контракт API.

Новую выдачу портал начинает с первого настроенного агента и при неудаче переходит к следующему. Перед отправкой сохраняются все возможные получатели. Продление обычной пары и отзыв направляются только зафиксированным получателям этой выдачи; очистка завершена после подтверждения каждого. Репликация изменений выполняется AD.

Для новой выдачи переход к следующему агенту допускается при отказе, недоступности или непроверенном ответе. Сохраняются тело, request_id, sequence и expires_at; timestamp/nonce и подпись создаются заново. Записанный получатель с неизвестным результатом остаётся адресатом отзыва. Подписанный probe имеет лимит 3 секунды, AD-команда — отдельный конечный бюджет портала, по умолчанию 130 секунд. Закреплённые отзывы другому DC не переадресовываются.

Отдельный support API описан в ''C:\2fa\agent\docs\support-api.md'' (в дистрибутиве также ''docs\support-api.md''). Capability ''support_all_v1'' обязательна. Support-выдача снимает ограничение по рабочим станциям на настроенный срок supportDurationSeconds (60 секунд по умолчанию); после срока или отзыва устанавливается только ''2FA-BLOCK''. Существующие права Windows и исключения администраторов/2fabypass сохраняются. Одновременное смешение support и обычной пары запрещено; sequence общий по AD user GUID.

API работает **только по HTTPS на порту 8443** по умолчанию, минимум TLS 1.2; открытого HTTP и перенаправления с HTTP нет. Все маршруты: ''POST'', ''Content-Type: application/json'', тело — JSON-объект не более 16 KiB, без query string. Доступ проверяется по реальному IP соединения и HMAC; ''X-Forwarded-For'' не используется для допуска.

Мобильный сервер должен доверять выпустившему сертификат CA и проверять цепочку, срок и DNS-имя сертификата. Подключаться по FQDN из настроек, проверку сертификата не отключать. Для доверия используется публичная цепочка ''C:\2fa\agent\tls\ca-chain.pem''; закрытый ключ с DC не передаётся. Эта настройка HTTPS относится к API агентов; веб-панель мобильной авторизации не меняется.

===== Маршруты =====

^ Маршрут ^ Ключ ^ Поля тела ^ Действие ^
| ''/v1/grants'' | mobile | request_id, sequence, login, computer, expires_at | Добавить ПК / продлить разрешение |
| ''/v1/revocations'' | mobile | request_id, sequence, login, computer | Отозвать указанную пару |
| ''/v1/support/grants'' | mobile | request_id, sequence, login, expires_at | Support-допуск на supportDurationSeconds, по умолчанию 60 секунд |
| ''/v1/support/revocations'' | mobile | request_id, sequence, login | Полностью вернуть запрещающую заглушку |
| ''/v1/status'' | mobile | ''{}'' | Статус экземпляра |

В ''config.json'' агента задаётся ''allowedIPs'' — список точных IP мобильного сервера, которым разрешено обращаться к API. Установщик на каждом сервере генерирует отдельный случайный HMAC-секрет (32 байта / 64 hex-символа) и записывает его в ''apiSecretHex'' защищённого ''config.json''. Администратор переносит этот секрет в настройки соответствующего агента на портале; в дистрибутиве рабочего секрета нет.

Ключ ''mobile'' соответствует ''apiSecretHex'' и разрешён только с IP из ''allowedIPs''. Массовые изменения и создание группы выполняются только локальными командами администратора на самом DC; команды приведены в ''C:\2fa\docs\instruction.txt''.

===== Настройка срока доступа =====

В ''C:\2fa\agent\config.json'': ''grantDurationSeconds'' — целое от 30 до 600, по умолчанию 300; ''supportDurationSeconds'' — целое от 30 до 180, по умолчанию 60. При отсутствии полей действуют эти значения по умолчанию. Дроби, строки и значения вне диапазонов запрещены.

''/v1/status'' возвращает ''grant_duration_seconds'' и ''support_duration_seconds''. Портал читает срок перед первой отправкой; на участвующих агентах значения должны совпадать. После начала доставки общий expires_at не меняется из-за повтора или другого адресата. Диапазон 30–600/30–180 относится к настройке, а не к оставшемуся времени доставки до expires_at.

Конфиг читается при запуске. Для ручного изменения дождаться завершения текущих окон и очистки, изменить значения на всех агентах и перезапустить процессы; таймеры не восстанавливаются после перезапуска.

===== Время ожидания =====

По умолчанию: не больше 100 одновременных соединений, 5 секунд на получение TLS/заголовков/всего тела от принятия TCP. Соединение закрывается после ответа. Параметры — ''maxConnections'' и ''requestReceiveTimeoutSeconds''.

''queueWaitTimeoutSeconds: 2'' ограничивает ожидание команды в очереди; фоновая проверка выполняется раз в секунду. Просроченная команда получает 503 без начала записи AD. ''processTimeoutSeconds: 30'' — отдельный срок одного процесса PowerShell; запрос может использовать несколько процессов. Таймаут отправителя не отменяет начатую запись, поэтому ответ 504 не гарантирует отсутствие изменений AD. Слишком короткое ожидание портала может привести к отправке резервному агенту, пока основной ещё работает.

Проверить синхронизацию часов: окно HMAC не увеличивает настроенный срок выдачи.

===== Подпись запроса =====

^ Заголовок ^ Содержимое ^
| ''X-2FA-Key-Id'' | ''mobile'' |
| ''X-2FA-Timestamp'' | Unix-время отправки, целые секунды |
| ''X-2FA-Nonce'' | 16 случайных байт в виде 32 строчных hex-символов |
| ''X-2FA-Signature'' | HMAC-SHA256, 64 строчных hex-символа |

Ключ HMAC — **32 бинарных байта после hex-декодирования секрета**, а не строка из 64 символов. Каноническая строка содержит шесть строк UTF-8, разделённых LF, **без завершающего перевода строки**:

<code>
POST
/v1/grants
AGENT_ID
UNIX_TIMESTAMP
NONCE_HEX
SHA256_RAW_BODY_HEX
</code>

Третья строка — точный ''agentId'' получателя; последняя — SHA-256 исходных байтов тела, в нижнем hex-регистре. Для каждого адресата брать agentId и секрет из его настроек. JSON сериализовать один раз, затем подписать и отправить именно эти байты.

Допустимое отклонение часов по умолчанию — 30 секунд. Повтор nonce отвергается. При повторе доставки создать новый nonce/timestamp/подпись, но сохранить прежние тело, ''request_id'', ''sequence'' и конечный срок.

===== Подпись ответа =====

Ответ после успешной аутентификации содержит ''X-2FA-Agent-Id'' и ''X-2FA-Response-Signature''. Каноническая строка для HMAC тем же бинарным ключом:

<code>
RESPONSE
AGENT_ID
REQUEST_NONCE
HTTP_STATUS
SHA256_RAW_RESPONSE_BODY_HEX
</code>

Клиент проверяет ожидаемый agentId, nonce отправленного запроса, фактический HTTP-статус и исходные байты ответа. Ошибки до аутентификации могут быть неподписанными; они не означают успех операции.

===== Выдача и продление =====

<code json>
{
  "request_id": "4c5b8de6-b4b9-4e10-a2c2-86b8f4f24c30",
  "sequence": 1001,
  "login": "ivanov-dd",
  "computer": "IVANOV-2121",
  "expires_at": "2026-11-05T15:05:00Z"
}
</code>

Дата в примере иллюстративная: отправитель вычисляет актуальный срок UTC, строго ''YYYY-MM-DDTHH:MM:SSZ'', больше текущего и не дальше настроенного grantDurationSeconds от часов агента. Конечный срок сохраняется при повторе, включая обращение к резервному агенту после недоступности основного. ''login'' — простой sAMAccountName до 20 символов; ''computer'' — NetBIOS-имя до 15 символов. UPN и DOMAIN\user не поддерживаются. Заглушку ''2FA-BLOCK'' выдавать как компьютер нельзя.

''request_id'' — UUID команды. ''sequence'' — целое число от 1 до 9007199254740991, возрастающее для каждой новой команды пользователя, включая отзыв. Общий возрастающий счётчик сервера также подходит. Повтор с прежним ID и тем же телом не продлевает доступ; новое подтверждение использует новый ID, больший sequence и новый срок. Запоздалая новая команда со старым номером получает 409.

При выдаче сохраняются прежние разрешённые компьютеры. Истечение любого местного таймера пользователя заменяет **весь список** заглушкой и отменяет остальные его местные таймеры. Открытые сеансы Windows/RDP не завершаются.

===== Досрочный отзыв =====

<code json>
{
  "request_id": "c8d9e078-c13d-497d-a315-c69620edf83a",
  "sequence": 1002,
  "login": "ivanov-dd",
  "computer": "IVANOV-2121"
}
</code>

Удаляется только указанный ПК; при отсутствии добавляется заглушка. Местный таймер этой пары отменяется. Исключения применяются и к отзыву: администраторы и прямые участники ''2fabypass'' не изменяются.

===== Ответы и статус =====

<code json>
{"ok":true,"result":{"status":"granted","request_id":"...","user_id":"...","login":"ivanov-dd","computer":"IVANOV-2121","sequence":1001,"expires_at":"..."}}
</code>

^ result.status ^ Значение ^
| granted / revoked | Изменение подтверждено на локальном DC |
| excluded | Пользователь исключён, AD не изменён |
| already_processed | Повтор известной команды; см. original_status и currently_active |

''currently_active'' сообщает о действующем таймере данного процесса, а не о сеансе Windows или состоянии другого DC. Успешные результаты команд хранятся десять минут; максимальные sequence пользователей — до перезапуска. Старый sequence запрещает повторное выполнение и после удаления результата из кэша.

Статус ''/v1/status'': ''agent_id'', ''enabled'', ''ready'', ''active_grants'', ''pending_cleanup'', ''queued_requests'', ''bulk_running'', ''last_directory_error'', ''server_time'', ''state_storage: "memory"'', ''logging_error'', ''dropped_log_records''. При ''bulk_running: true'' доступен статус, новые изменяющие операции получают 409. При ''ready: false'' выдача разрешений запрещена. Ошибка журналирования отражается в ''logging_error'' (''null'' либо ''log_write_failed'') и счётчике потерянных записей; она не останавливает отзыв разрешений.

Ошибка: ''{"ok":false,"error":{"code":"http_503","message":"..."}}''. Основные HTTP-коды: 400 — неверные поля, 401 — подпись/время, 403 — IP/ключ не допущен, 404 — маршрут/пользователь не найден, 409 — конфликт/повтор/массовая операция, 413 — слишком большое тело, 429 — переполнение очереди, 502–504 — ошибка или таймаут AD/адаптера. Нельзя считать HTTP 200 успехом без проверки подписи и result.status.

Таймаут не доказывает отсутствие изменения в AD. При потере ответа повторять доставку с теми же телом, ID, sequence и сроком; менять только timestamp, nonce и подпись. При сообщённой агентом неподтверждённой записи проверить очистку (''pending_cleanup''). Сознательно начатая новая попытка после такой ошибки получает новый ID и больший sequence; исходный срок нельзя продлевать без нового подтверждения второго фактора.

===== Повтор ручного отзыва после ошибки =====

После временной ошибки ''/v1/revocations'' или ''/v1/support/revocations'' допустим повтор с теми же request_id, sequence и телом на том же агенте. Перед записью проверяются fingerprint, исходный AD GUID и то, что номер всё ещё последний для пользователя. Если уже принята более новая команда либо прежний логин теперь относится к другому GUID, старый отзыв получает 409 без повторной записи. Выключенный режим и массовый обход по-прежнему запрещают повтор.

Актуальный неудавшийся отзыв сохраняется в ограниченном RAM-кэше и после обычных десяти минут; после успешного повтора действует обычный срок хранения результата. Ошибка выдачи такого повторного исполнения не допускает. При каждой доставке нужны новый timestamp, nonce и HMAC, но прежнее тело команды.

HTTP-отзыв портал отправляет только по кнопке пользователя до исходного срока. Плановое истечение настроенного срока обслуживает агент; локальный expired портала не подтверждает физическую очистку AD.

===== Два агента и перезапуск =====

  * Новые выдачи идут по приоритету настроек. Продление и отзыв закреплены за возможными получателями исходной выдачи; между агентами нет обмена таймерами.
  * Каждый процесс хранит только свои таймеры и историю. После перезапуска они теряются, режим берётся из startEnabled, а записи AD остаются.
  * Портал хранит сроки и возможных получателей. Ручной отзыв повторяется по кнопке до исходного дедлайна; плановый HTTP-отзыв не отправляется. Локальные таймеры агента не восстанавливаются; при недоступном DC или задержке репликации физическое закрытие строго в срок не гарантируется.
  * Журналы в ''C:\2fa\logs'' не восстанавливают разрешения. Открытые сеансы Windows/RDP продолжаются.

Порядок отправки и постоянную историю получателей поддерживает мобильный портал.

===== Порядок подготовки портала =====

  - В allowedIPs каждого агента указать исходящий IP портала. После установки перенести в настройки портала URL, agentId, сгенерированный установщиком HMAC-секрет и доверие CA. Проверить HMAC по ''hmac-test-vector.json''.
  - Проверить нужный экземпляр подписанным ''/v1/status'': для выдачи нужны ''ready: true'', ''enabled: true'', ''bulk_running: false''. Ответ резервного агента не требуется для работы с основным.
  - После подтверждения второго фактора сохранить команду с новым UUID, следующим sequence пользователя и expires_at; отправить основному агенту. При его недоступности отправить исходное тело резервному с новой подписью для получателя.
  - Проверить TLS, подпись ответа, HTTP и result.status. ''granted'' подтверждает новую выдачу; ''excluded'' означает отсутствие изменения. У ''already_processed'' проверить original_status/currently_active.
  - При потере ответа основного агента обратиться к резервному с теми же ID/sequence/сроком и новой подписью. Если срок прошёл, устаревшую выдачу не отправлять. Транспортная ошибка сама по себе не продлевает доступ.
  - Только по кнопке создать досрочный отзыв с новым UUID и большим sequence каждому возможному получателю. Повторять тому же адресату до подтверждения либо исходного дедлайна; не подменять его другим DC. По сроку портал завершает окно локально без HTTP-отзыва и подтверждения AD; очистку выполняет агент.

''/v1/status'' не проверяет конкретную пару: только общие счётчики. Агент не завершает открытые сеансы Windows/RDP и не выдаёт токены авторизации портала.
